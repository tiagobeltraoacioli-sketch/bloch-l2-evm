# Reth node integration boundaries

This is an implementation dependency map, not evidence that a node exists.
It refers to Reth revision `8eb210175687c9f0c889a3b6795c16781d830e3a` and the
separately pinned host integration in `integrations/reth-execution`.

## Storage before node launch

The implemented boundary executes original signed envelopes over
`StateProviderDatabase` and converts successful execution to `BundleState`.
The storage test now uses Reth's actual database provider to
calculate `state_root_with_updates` over the hashed bundle, write plain
state and reverts, write hashed state and trie updates, and commit the same
transaction. Fresh and reopened providers expose the identical root and values
for the exercised signed deploy/set/clear scenario. This remains test harness
plumbing rather than a node storage service.

Retain the original snapshot until root calculation and revert capture finish.
On any error, abort the candidate transaction. Uncommitted transaction drop,
successful commit and orderly close/reopen are exercised. A signed self-destruct
test also deletes unread storage, then restores the original state root using
only persisted changesets after reopening. It retains history; canonical unwind
still needs block metadata and custom primitives. Existing execution-boundary tests
reject malformed input but do not replace those storage gates. A new
read transaction proves visibility after commit but does not prove process
restart recovery. Synthetic funding in these tests is not authenticated native
derivation.

## Executor and builder

Reth's `ConfigureEvm` requires a `BlockExecutorFactory`, a `BlockAssembler`,
custom node primitives and block/next-block context. The pinned Alloy executor
also exposes transaction execution before conditional commitment. Bloch's
current whole-block entry point cannot simply be substituted for that interface.

The shared core now provides `SignedBlockBuilder`; whole-block verification uses
the same incremental kernel. Header validation, committed `BLOCKHASH` history,
EIP-4788 and deposits execute once, followed by sparse candidate execution and
final ledger/head writes. A candidate's fee and conservation checks run inside
its disposable overlay before publication. Tests cover rejection/skip atomicity,
late fee-vault provider failure, sparse storage merging and agreement with
whole-block execution; the real Reth storage test also uses this builder.

`BlochBlockExecutorFactory` now implements the actual Alloy SDK factory and
executor traits over the supplied `BlochEvm`. It reauthenticates canonical signed
envelopes, ignoring cached recovered senders and prebuilt transaction environments.
Rejected and skipped candidates consume bounded authentication attempts/bytes.
Owned results are bound to an executor identity and database generation; commits
and mutable EVM access invalidate older candidates. The checked commit method
returns an error on misuse. The SDK's infallible commit poisons the executor and
returns zero gas; all later execution/finalization then fails. No invalid result
publishes state or a receipt. The explicit V2 primitive/configuration/assembler
adapters are described below; full node wiring remains open.

The SDK requires `EvmFactory::Evm<DB, I>` to expose that exact database and
inspector, and `StateDB` requires mutable `Database + DatabaseCommit`, not
`DatabaseRef`. The shared core now supplies `prepare_transaction_effects` over
that mutable boundary. It prepares owned EVM/accounting effects with all reads
finished before its infallible commit; `BlockSession` calls the same function.
The staged `executor::lifecycle` API now also supplies the shared header,
deposit and finalization phases around the actual supplied EVM system call.
The host's `sdk_preparation` tests execute original signed candidates in the
actual Alloy EVM factory over revm `State`, observe real inspector callbacks,
and prepare/commit through that same EVM/database, including vault recreation.

The host now provides `BlochEvmFactory`, `BlochEvm` and `BlochContext` with
exact supplied database and inspector types. Its context reads `BLOCKHASH` from
the configured committed Bloch ring without journal warming; opcode window and
gas rules, execution handlers and precompiles remain upstream implementations.
Tests cover window boundaries, missing head, provider failures and inspector
callbacks. A differential test uses history generated by actual core blocks and
compares signed execution with the core despite conflicting database hash cache.
The block executor installs the immutable window captured by the core prefix
before the beacon call and restores it before each candidate. A contract can
legitimately modify a custom block-info account during execution; reading the
live ring would diverge from the portable kernel. An adversarial deployment
regression proves the frozen window remains identical. Standalone EVM users
must install their lifecycle window explicitly.

The staged lifecycle now preserves this order in the supplied EVM: validate
header and update the ring, ensure the beacon predeploy, execute the beacon
system call, apply authenticated deposits, execute signed candidates, then
record burns and the final head. Five signed-block differential fixtures cover
these phases with both InMemoryDB and revm State, including State bundle changes.
Each prepared phase finishes reads before commit; any later failure requires
discarding the provisional block database. There is no generic rollback.
The factory connects these phases to owned results and typed user receipts.
`finish_bloch` additionally preserves the core result awaiting a calculated root;
the generic SDK `finish` returns its normal EVM/block result without inventing a
state root. Configuration must match the canonical Bloch environment exactly.
The executor restores upstream canonical precompiles before execution, so a
caller-modified precompile map does not silently change consensus rules.

Pool recovery is not an authentication boundary. Admission and execution must
retain canonical signed bytes; reauthenticate them rather than trusting a
cached sender or an independently supplied transaction environment. RPC call
simulation must use the same hardfork, fee recipient and Bloch block context,
while keeping its state changes ephemeral.

## Header and receipts require a new domain

The current `L2Header::hash` hashes a fixed-width 200-byte encoding, including
deposits and state roots. `HeadRecord` stores the fields needed to reconstruct
that hash using the containing state root. It does not store transaction or
receipt roots. Ethereum's ordinary RLP header has a different identity.

Custom primitives must preserve the existing identity for the existing domain.
Adding transaction/receipt commitments requires a separately versioned execution
domain and explicit migration, including head storage, reconstruction, witness
execution and public inputs. Extra RPC fields cannot supply those commitments.
No current domain or production consensus is activated by this integration.

The independent [V2 node format](NODE-V2-FORMAT.md) now defines tagged RLP
header/body/block primitives, parent-state-root linkage and signed-body/receipt
consistency checks. Its codecs are bounded and preserve V1 identities. Explicit
V2 genesis/head storage and signed portable/witness execution now commit actual
transaction/receipt roots before computing the state root. Authenticated domain
initialization and node storage/consensus wiring remain required. The explicit
`BlochNodeBlockExecutorFactory` now uses the same staged V2 header policy on the
supplied EVM. It retains only accepted signed bytes and compares SDK receipts
with core-derived receipts before committing metadata. `finish_node` preserves
the resulting `FinishedNodeBlock` for independent root calculation.
In particular, Bloch block gas currently includes deposit gas, while deposits
are not Ethereum signed transactions. The new format must specify deposit body
representation, receipt indexing and cumulative gas semantics together. Do not
invent ordinary Ethereum receipts for deposits, or silently omit deposit gas to
fit an Ethereum header. Logs and outputs are already available in `TxOutcome`;
the standalone executor now emits canonical typed `ReceiptEnvelope` values for
user transactions, with cumulative **user** gas. The block result includes deposit
gas separately; its total can exceed the last user receipt. No deposit receipt is
fabricated. Committed receipt roots/order and node/RPC treatment still require
the custom format. Ordinary Ethereum block/receipt validation cannot be reused
unchanged for these semantics.

## Acceptance evidence

A developer acceptance run must start the custom Reth node, submit a signed
deployment through its real RPC/pool, call the contract, inspect receipts/logs
and storage, restart, and repeat the reads. It must reject malformed/replayed
transactions, preserve state after rejected payloads, and exercise reorg/unwind.
The native derivation and proof gates in [the delivery plan](EVM-DELIVERY-PLAN.md)
remain separate requirements. Compiling or launching upstream's `custom-evm`
example does not close any Bloch-specific node gate.

## Actual V2 Reth configuration and assembly

`BlochNodePrimitives` implements the pinned full-node trait with custom tagged
header/body/block adapters, compact header storage, and the upstream compactable
transaction/receipt representations. Internal serde is a bounded RLP byte transport,
not the eventual Ethereum JSON-RPC schema. Sealing preserves the portable V2 hash.
`BlochRethBlockExecutorFactory` converts these node representations through the
existing V2 executor; signature authentication and commit leases remain shared.

`BlochEvmConfig` implements `ConfigureEvm` and supplies canonical block/next-block
environments plus authenticated-body contexts. Its assembler reads the committed
head from bundle-over-provider storage and checks parent/body/receipts/context.
The root arrives independently calculated by the builder. No post-root metadata
write is permitted. Focused tests exercise real signed execution with revm State,
Reth configuration traits, bundle assembly and adverse inputs. They are not an
end-to-end launched node or a replacement for import consensus validation.

Reth's chain-specific `BlockBodyReader`/`BlockBodyWriter` must preserve deposits
in durable custom storage alongside the separately stored signed transactions.
`into_ethereum_body` is only a lossy RPC projection. The upstream EthStorage
implementation is for Ethereum bodies and cannot serve the Bloch body format.
Canonical unwind, restart and crash recovery must include this extra body data.
